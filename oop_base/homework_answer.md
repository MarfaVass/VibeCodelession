# Ответ на вопросы домашнего задания VPb04 «Основы объектного мышления»

Проект OOP_base — консольная система управления задачами Todo на Python
(классы `User`, `Project`, `Task`). Данные хранятся в памяти,
сторонние библиотеки не используются.

## Какие классы созданы

1. **`User`** — пользователь системы.
2. **`Project`** — проект, объединяющий задачи.
3. **`Task`** — отдельная задача.

## Атрибуты и методы классов

### Task

Атрибуты (все приватные):

- `_id` — ID задачи (назначается проектом при добавлении);
- `_title` — название задачи;
- `_description` — описание задачи;
- `_due_date` — срок в формате `YYYY-MM-DD` или `None`;
- `_status` — статус: `todo`, `in_progress` или `done`.

Методы и свойства:

- `change_description(new_description)` — изменить описание;
- `change_due_date(new_due_date)` — изменить срок;
- `set_status(new_status)` — установить статус;
- `complete()` — отметить задачу выполненной;
- свойства `id`, `title`, `description`, `due_date`, `status` — для чтения;
- свойство `info` — сводка о задаче одной строкой.

### Project

Атрибуты (приватные):

- `_id` — ID проекта (генерируется автоматически счетчиком класса);
- `_name` — название проекта;
- `_tasks` — список задач проекта;
- `_next_task_id` — счетчик для выдачи ID задачам.

Методы и свойства:

- `add_task(title, description, due_date=None)` — добавить задачу;
- `remove_task(task_id)` — удалить задачу по ID;
- `get_task_by_id(task_id)` — найти задачу по ID (или `None`);
- `mark_task_status(task_id, status)` — изменить статус задачи;
- `complete_task(task_id)` — отметить задачу выполненной;
- `find_tasks_by_status(status)` — отобрать задачи по статусу;
- свойство `tasks` — список задач (копия);
- свойство `progress` — процент выполненных задач (пустой проект — `0`);
- свойство `info` — сводка о проекте одной строкой.

### User

Атрибуты (приватные):

- `_name` — имя пользователя;
- `_projects` — список проектов пользователя.

Методы и свойства:

- `create_project(name)` — создать проект с проверкой на дубликат названия;
- `add_project(project)` — добавить уже созданный проект;
- `remove_project(project_id)` — удалить проект по ID;
- `get_project_by_id(project_id)` — найти проект по ID (или `None`);
- `find_project_by_name(name)` — найти проект по названию (или `None`);
- свойства `name`, `projects` (копия списка), `info`.

## Как связаны объекты

Иерархия: `User` содержит список проектов, `Project` содержит список задач.

```text
User ──owns──> Project ──owns──> Task
```

- Пользователь владеет проектами: `User._projects` — это список объектов
  `Project`.
- Проект владеет задачами: `Project._tasks` — это список объектов `Task`.
- Связь направлена только сверху вниз: задача ничего не знает о проекте
  и пользователе, проект ничего не знает о пользователе.

## Как реализовано объектное взаимодействие

- Объекты общаются только через публичные методы и свойства.
  Например, пользователь создает проект методом `create_project`, проект
  создает задачу методом `add_task`, а выполнение задачи из уровня проекта
  выглядит так: `project.complete_task(task.id)`.
- Данные защищены: атрибуты приватные (с `_`), списки `tasks` и `projects`
  наружу отдаются как копии, поэтому внешний код не может подменить
  содержимое в обход методов.
- ID задач генерирует проект (передает очередной ID конструктору `Task`);
  ID проектов генерирует счетчик на уровне класса `Project`.
- При проверке ввода объект сам отвечает за свои данные: `Task` проверяет
  строку даты и статус, `Project` — название, `User` — имя и дубликаты
  проектов. Некорректные данные приводят к `ValueError` или `KeyError`
  с понятным сообщением.

## Какие принципы ООП использованы

- **Инкапсуляция** — данные классов спрятаны в приватные атрибуты
  (`_title`, `_tasks`, `_projects`...), доступны через методы и
  `@property`; изменение возможно только через методы с проверкой данных.
- **Абстракция (объектное мышление)** — каждый класс отвечает за одну
  сущность предметной области и собственные действия: задача не решает
  вопросы проекта, проект — вопросы пользователя.
- Естественное следствие связей — **агрегация/композиция**: пользователь
  состоит из проектов, проект состоит из задач.
- Методы уровня класса для генерации ID (`Project` хранит общий счетчик
  ID проектов) и статические методы проверки ввода (`_check_text`,
  `_check_name`).

Чего в проекте сознательно нет — наследования и полиморфизма: в этой
предметной области три класса не являются родственными типами, и добавлять
искусственную иерархию только «для галочки» было бы ошибкой проектирования.

## Как проверить работу программы

1. Запусти демо-сценарий из папки `oop_base/`:

   ```powershell
   python main.py
   ```

   Он автоматически показывает создание пользователя и проектов, добавление
   задач, изменение описания и срока, смену статусов, прогресс проекта до
   и после выполнения задач, поиск по ID, фильтрацию по статусу, удаление
   задачи и проекта, а также реакцию на некорректные данные (пустое название,
   дубликат проекта, неверная дата, неизвестный статус, повторное удаление).

2. Запусти тесты:

   ```powershell
   python -m unittest
   ```

   38 тестов проверяют: создание объектов и автоматическую генерацию ID,
   валидацию названий, дат и статусов, дубликаты проектов, прогресс пустого
   проекта, поиск и удаление объектов, защиту списков от подмены снаружи.

# Manifest — отчет о выполнении ДЗ VPb04 «Основы объектного мышления»

Проект: OOP_base (консольный Todo на Python: классы `User`, `Project`, `Task`).

## 1. Что попросил

Основной промт для генерации программы:

> Напиши учебную консольную систему управления задачами Todo на Python.
> Реализуй три класса: `User` (пользователь, владеет списком проектов),
> `Project` (проект, объединяет задачи), `Task` (отдельная задача).
> Используй конструкторы `__init__`, `self`, приватные атрибуты, методы
> объектов, свойства `@property`, автоматическую генерацию ID, проверку
> входных данных, взаимодействие объектов через методы.
> Обязательно реализуй: создание пользователя и проектов; добавление и
> удаление проектов; создание и управление задачами; поиск задач и проектов
> по ID; изменение описания и срока задачи; изменение статуса задачи;
> расчет прогресса проекта.
> Не используй базу данных, API, GUI, авторизацию, ORM, асинхронность и
> сторонние библиотеки — данные хранятся в памяти. В конце `main.py`
> добавь демонстрационный сценарий, который выполняется автоматически
> при запуске. Дополнительно подготовь тесты на стандартном `unittest`.

Полное техническое задание зафиксировано в `architecture.md` до написания кода.

## 2. Что получил

Реализация соответствует архитектуре из `architecture.md`:

- классы `Task`, `Project`, `User` в `main.py` с теми же атрибутами,
  методами и свойствами, что описаны в ТЗ (включая свойства `progress`,
  `tasks`, `projects`, `info` и методы поиска/удаления по ID);
- приватные атрибуты и `@property` — данные защищены, списки наружу
  отдаются копиями;
- авто-ID: проекты получают ID от счетчика класса, задачи — от проекта;
- валидация входных данных: пустые строки, некорректная дата, неизвестный
  статус, дубликат проекта → `ValueError`; удаление несуществующего объекта
  → `KeyError`; поиск несуществующего по ID → `None` — как в ТЗ;
- иерархия `User → Project → Task` со связью только сверху вниз;
- демонстрационный сценарий в конце `main.py` проходит все 8 пунктов из ТЗ;
- `python -m unittest`: 50 тестов в `tests/test_oop.py` — все проходят
  (фактический запуск);
- база данных, API, GUI и сторонние библиотеки не используются.

Отклонения от архитектуры, найденные при повторной проверке, были исправлены
(см. раздел 3); на момент сдачи документация и код согласованы.

## 3. Что исправил

История честная: архитектуру и код генерировал Claude Code (ИИ-агент),
а проверки запускались в реальном окружении; исправления при необходимости
вносились на этапе проверки. Пользователь при исправлениях не участвовал.

Фактически найденные и исправленные проблемы:

1. **Строгий формат даты.** Первый тестовый прогон (38 тестов) дал 1 ошибку:
   тест `test_bad_due_date_raises` ожидал `ValueError` для `'20261120'`,
   но `datetime.date.fromisoformat` в Python 3.11+ принимает и формат без
   разделителей. ТЗ требовало строго `YYYY-MM-DD`, поэтому в
   `Task._parse_date` добавлена предварительная проверка формата
   регулярным выражением. После правки все 38 тестов проходят.
2. **Нумерация шагов демо-сценария.** Первый прогон `main.py` показал, что
   фильтрация по статусу выводилась без номера раздела, и нумерация
   перескакивала с 5 на 7. Добавлен заголовок раздела 6.
3. **Кодировка при запуске в пайпе.** При захвате вывода через
   перенаправление русский текст выглядел как кракозябры — это артефакт
   кодировки stdout piped-режима Windows (cp1251), а не ошибка программы:
   при обычном запуске в консоли VS Code / PowerShell вывод корректен.
   В коде ничего менять не потребовалось.

Повторная проверка перед сдачей (тоже выполнена автоматически, без
участия пользователя) выявила и устранила:

4. **Обращение к приватному методу.** `User.create_project` вызывал
   приватный `Project._check_name(name)`. Исправлено: сначала проверяется
   дубликат названия, затем объект создается конструктором `Project` —
   валидация названия остается только в нем, без обращения к приватным
   методам. Неудачная попытка создать дубликат не расходует ID проекта
   (за этим закреплен отдельный тест).
5. **`bool` проходил проверку ID.** В Python `bool` — подкласс `int`, поэтому
   `isinstance(True, int)` равен `True` и `get_task_by_id(True)` не считался
   некорректным. В проверки ID задач и проектов (4 места) добавлено явное
   исключение `bool`.
6. **Демо не выполняло заявленную проверку.** Комментарий обещал проверку
   пустого имени пользователя, а фактически создавался только валидный
   пользователь. Добавлен блок `try/except` с `User("   ")`.
7. **Документация расходилась с кодом.** В `architecture.md` счетчик ID
   задач был помечен как class-level (в коде — экземплярный), не был
   описан счетчик проекта и хранение срока как `datetime.date`; уточнено,
   что копии списков поверхностные и что статусы проверяются только на
   допустимость значения. В `README.md` версия Python указана по факту
   проверки (3.14.8, а не «3.12»); ID задач описаны как уникальные в
   пределах проекта. В `homework_answer.md` уточнены хранение `_due_date`,
   уровень счетчика и разграничение композиции и агрегации.
8. **Дополнены тесты** (+11, итого 49): некорректные типы названий,
   описаний и статусов; некорректная дата при изменении; пустое описание
   при добавлении задачи через `Project`; `bool` как ID задач и проектов;
   независимость счетчиков разных проектов; невозврат использованного ID
   после удаления; защита свойств только для чтения.
9. **Точечная финальная корректировка.** Порядок действий в
   `User.create_project` изменен: дубликат проверяется до создания объекта
   (см. п. 4); добавлен тест, что неудачная попытка создать дубликат не
   расходует ID проекта (+1 тест, всего 50). В README объединены
   дублирующиеся пункты о поиске по ID и уточнена проверенная версия
   Python (3.14.8). В `homework_answer.md` уточнено описание композиции:
   это основной сценарий владения, код не запрещает создавать
   `Task`/`Project` отдельно, а `User.add_project()` позволяет добавить
   уже созданный проект. Документация повторно сверена с кодом.

## 4. Вывод

Описывать архитектуру до кода оказалось полезно и несложно: сущности
учебные, атрибуты и методы очевидны, а ТЗ «приватные атрибуты +
`@property` + валидация» само по себе диктует структуру классов.
Главные усилия ушли не на сами классы, а на:

- точную формулировку контрактов (что возвращает поиск при неудаче —
  `None` или исключение; что считать прогрессом пустого проекта);
- полноту проверки входных данных (пустые строки, пробелы, типы, форматы дат,
  статусы, дубликаты) — именно здесь без ТЗ легко пропустить кейсы;
- строгость формата даты: стандартная библиотека «прощает» больше форматов,
  чем указано в ТЗ, и это проявилось только в тестах.

Что можно улучшить дальше (осознанно не делаем в учебном ДЗ):

- сохранение данных на диск (JSON) и/или в базу данных;
- интерактивное консольное меню вместо автоматического демо;
- исключения-классы собственного типа (`TaskError`, `ValidationError`) вместо
  стандартных `ValueError`/`KeyError`;
- сортировка задач по сроку и подсветка просроченных;
- переход на `enum.Enum` для статусов вместо кортежа строк.

# Отчёт о проекте: VK-бот Smart Body Academy

Проект: виртуальный администратор сообщества ВКонтакте Академии умного тела Андрея Новикова (smartbodyacademy.ru).
Статус: **реализован, протестирован, документирован**. Дата завершения: 2026-11-03.

---

## 1. Задача проекта

Разработать учебного VK-бота, который:

1. определяет категорию входящего клиента (четыре направления Академии);
2. знакомит пользователя с соответствующим направлением и отвечает на вопросы **на основании официального сайта**, а не «из головы» модели;
3. принимает предварительные заявки по отдельным сценариям для каждой категории и сохраняет их в SQLite;
4. работает на локальной LLM (Ollama, модель `qwen2.5:3b-32k`) и не падает при отказах внешних компонентов.

Категории клиентов: **частный специалист** (обучение тренеров), **фитнес-клуб/студия** (корпоративное обучение), **международная организация** (приглашение преподавателя, общение на английском), **частный клиент** (персональные тренировки).

## 2. Выбранное техническое решение

| Компонент | Решение |
|---|---|
| VK | vkbottle 4.11, long polling, текстовые кнопки с payload |
| LLM | Ollama `qwen2.5:3b-32k` (локальная, из существующего `.env`), вызов `requests` → `asyncio.to_thread` |
| Знания | Локальная база Markdown-документов с метаданными (тема, категория, источник-URL, дата сбора) |
| RAG | Простой ключевой поиск (без эмбеддингов и векторных моделей — база составляет 10 документов/десятки фрагментов, векторный поиск избыточен по ТЗ) |
| Сценарии заявки | Единый конечный автомат `BookingFlow`, настраиваемый спецификацией полей на категорию |
| Хранение | SQLite (модуль `sqlite3`), одна таблица `bookings` |
| Конфигурация | python-dotenv, все секреты в `.env` (в git не попадает) |
| Тесты | pytest 9 + pytest-asyncio, 71 тест, VK-токен и реальные сообщения не используются |

От прежней концепции («AI-консультант по пилатесу») сохранились и были переиспользованы: клиент Ollama с нормализацией ошибок (`bot/ai_client.py`), механизм текстовых промптов вне кода (`bot/prompts/*.txt`), схема гарантированного commit/close для SQLite, конфигурация на `Settings`/dotenv. Переработаны: база данных (новая схема под категории), системные промпты, добавлены база знаний, ретривер, классификатор и диалоговый менеджер.

## 3. Назначение основных модулей

| Модуль | Ответственность |
|---|---|
| `bot/main.py` | Сборка приложения из настроек, единственный VK-обработчик: извлекает текст/payload и делегирует менеджеру, отправляет ответы |
| `bot/manager.py` | Диалоговый менеджер: состояние пользователей (категория/ожидание/сценарий), команды, маршрутизация по категориям, RAG-ответы, сохранение заявок |
| `bot/categorize.py` | Классификация: фразы-якоря → счёт ключевых слов по уникальным токенам → AI-классификатор (жёсткий промпт, короткий ответ) → «неоднозначно» |
| `bot/booking/flow.py` | Конечный автомат заявки: шаги (имя → контакт → запрос → категорийные поля → подтверждение), валидация, пропуск необязательных полей, перехват попутных вопросов |
| `bot/knowledge/loader.py` | Разбор Markdown-документов, проверка обязательных метаданных, разбивка на абзацы-фрагменты |
| `bot/knowledge/retriever.py` | Поиск по фрагментам раздела категории (+ `common`): токенизация, стоп-слова, усечённые основы слов, порог релевантности, топ-5 фрагментов |
| `bot/ai_client.py` | Транспорт к Ollama: `/api/chat`, контекст-обёртка, нормализация ошибок (`UNREACHABLE/TIMEOUT/HTTP/MODEL/EMPTY`), трим до лимита VK, режим `classify` |
| `bot/prompts/` | `system.txt` — роль администратора и ограничения («не выдумывать», «не медицина»); `classify.txt` — правила классификации; редактируются без кода |
| `bot/storage/db.py` | SQLite: авто-создание БД/таблицы, обязательные поля (имя, контакт, категория), JSON-поле `details`, статусы |
| `bot/keyboards.py` | Клавиатуры: главное меню (4 направления + заявка + помощь), категорийная, подтверждение |

## 4. Применение AI

Модель отвечает пользователям бота; модель агента разработки — отдельная задача, к боту не подключается.

AI выполняет **три узкие функции**:

1. **Формулировка ответа (RAG-шаг).** Менеджер находит фрагменты ключевым поиском и передаёт модели только их (`ask(question, system_prompt, context=...)`). Системный промпт запрещает использовать факты вне фрагментов; если фрагментов нет — модель не вызывается вовсе, бот возвращает готовый честный отказ («информации нет, уточните у представителя»).
2. **Классификация (фолбэк).** Только если ключевые слова не определили категорию однозначно. Строгий промпт `classify.txt`: вернуть один код (`specialist|club|international|client` или `ambiguous`), `temperature=0.1`, `max_tokens=8`.
3. **Ответ на попутный вопрос во время заявки.** Вопрос направляется в RAG соответствующей категории, после чего сценарий продолжается с того же шага (`resume_after_answer`).

Гарантии против «выдумывания»: модель не получает всю базу; отсутствие фрагментов = отказ без вызова модели; промпт запрещает цены/расписание/медицинские советы; в базе знаний цены сверены автотестом с подтверждённым на сайте списком (`test_no_invented_prices_in_knowledge`).

## 5. Собственная программная логика (без AI)

Обычным кодом Python реализовано:

- команды и кнопки, приветствие, справка, меню;
- ключевой поиск по базе знаний (основной RAG-механизм — детерминированный);
- первичная классификация по ключевым словам и фразам-якорям;
- конечный автомат заявки: валидация имени/контакта, шаги, необязательные поля («пропустить»), обязательное поле клуба (название организации), подтверждение, отмена;
- хранение заявок и статусы;
- обработка всех отказов (Ollama недоступна, модель пустая, БД недоступна) — готовые тексты вместо падения.

## 8. Схема маршрутизации

```
                        ┌────────────────────────────┐
   сообщение/кнопка ──►│ команды: /start /menu /book │──► соответствующий сценарий
                        │  /help /cancel, подтвержд.  │
                        └────────────┬───────────────┘
                категория не выбрана │
                                     ▼
            ключевые слова/якоря ──► уверенно? ──да──► направление категории
                                     │ нет                     │
                                     ▼                        │
                          AI-классификатор ──► уверенно? ──да─┘
                                     │ нет/ошибка               │
                                     ▼                          ▼
                       один уточняющий вопрос          RAG: поиск в разделе
                       (кнопки «1–4»)                  категории → ответ модели
                                     │                          │
              кнопка направления ────┘            мало фрагментов → честный отказ
                                                  + предложение заявки /book
```

Переключение направлений доступно всегда (`/menu` или кнопки) — состояние категории сбрасывается корректно. Для категории `international` часть диалога и сценария заявки идёт на английском, модель отвечает на языке пользователя.

## 9. Сценарии сбора заявок

Общие поля: имя (обязательно), контакт (обязательно), суть запроса (необязательно) + категорийные поля:

- **специалист**: направление обучения, текущий опыт, формат обучения (все необязательные);
- **клуб**: название организации и город (обязательно), контактное лицо, число сотрудников, интересующая программа, пожелания;
- **международная организация** (на английском): организация (обязательно), страна/город, контактное лицо, формат мероприятия, тема и сроки;
- **частный клиент**: формат тренировок, способ занятий, пожелания.

Перед сохранением показывается сводка и запрашивается подтверждение («Отправить»/«да» или «нет»). Обязательный минимум заявки — только имя и контакт. Статус `preliminary` подчёркивает: обращение предварительное, согласование выполняет представитель Академии.

## 10. Роль Ollama и ограничения модели

Модель (`qwen2.5:3b-32k`, локальная) формулирует ответы по найденным фрагментам и классифицирует неоднозначные обращения. Она **не** хранит знания Академии — знания лежат в базе; она не вызывается, когда фрагментов нет; её ответы ограничены системным промптом. Недоступность Ollama нормализуется в пять причин, и бот объясняет это пользователю, оставаясь работоспособным: заявки и команды работают без AI.

## 12. Ограничения

- Только предварительные заявки; никакой записи на конкретное время и гарантий мест.
- База знаний снята 2026-11-03 вручную и не обновляется автоматически.
- Состояние диалогов в памяти процесса — после рестарта незавершённые заявки теряются (сохранённые остаются в БД).
- Ключевой поиск опирается на лексику; вопрос, сформулированный совсем иначе, чем документ базы, может дать пустой результат — это честно сообщается пользователю.
- Скорость и качество ответов зависят от локального железа; модель 3B может неточно формулировать текст (факты ограничены ретривером, но промпт — не гарантия).
- Нет административного интерфейса: заявки просматриваются в SQLite напрямую.

## 15. Адаптация под заказчика

Варианты дальнейшей адаптации бота под конкретного заказчика:

1. **Смена бренда/ниши**: заменить `bot/prompts/*.txt`, приветствия и интро в `bot/manager.py`, документы базы знаний в `bot/knowledge/documents/<категория>/`. Код сценариев не меняется.
2. **Другая модель LLM**: конфигурация `OLLAMA_URL`/`OLLAMA_MODEL` в `.env` — код не меняется (подойдёт любая совместимая с OpenAI-стилем /api/chat инсталляция Ollama на отдельном сервере).
3. **Новые категории клиентов**: добавить папку документов, строку `FIELD_SPECS` в `bot/booking/flow.py`, ключевые слова в `bot/categorize.py` и текст интро в `CATEGORY_INTRO`.
4. **Изменение полей заявки**: правка списка `FieldSpec` (вопрос, флаг «обязательно») в `bot/booking/flow.py` — схема БД (JSON `details`) изменений не требует.
5. **Английская/мультиязычная версия**: добавить документы на нужном языке и интро-тексты; классификация и RAG уже не зависят от языка, модель отвечает на языке пользователя.
6. **Интеграция с CRM персонала**: заменить вызов `db.save_booking` на отправку в CRM при сохранении `bot/manager.py:_submit_booking` (одна точка входа).
